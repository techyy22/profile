Computer Architecture Project

8-Bit ALU Design & Implementation

As part of my computer architecture and hardware coursework, I worked on the design and implementation of an 8-bit Arithmetic Logic Unit (ALU) for a custom CPU. Our class first defined the instruction set architecture (ISA), including the registers, instruction formats, memory operations, branching, and ALU operations that the processor would support.

The Goal

My responsibility was to design the ALU that would perform the arithmetic and comparison operations required by our ISA. The design needed to support operations including addition, subtraction, and set-less-than comparisons while integrating with the larger CPU datapath.

Rather than treating the ALU as an isolated circuit, I had to consider how it would interact with the register file, control logic, and the rest of the processor.

Design & Implementation

I designed the ALU as a minimum viable model capable of performing the core operations required by our instruction set. The design used digital logic to control the arithmetic operations and produce the appropriate output based on the selected ALU operation.

One of the more interesting challenges was combining the addition and subtraction logic. My professor challenged me to find a way to use shared logic for both operations rather than treating them as completely separate circuits. I worked through the logic and ultimately got the combined addition and subtraction design working.

Testing & Iteration

The project also taught me an important lesson about hardware testing. My original design successfully demonstrated the basic functionality of the ALU, but testing was not robust enough to catch an issue with the SLT (set-less-than) operation.

After identifying the problem, I was able to recognize where the original design fell short and use that experience to improve my approach to testing. The project reinforced that a circuit can appear to work correctly under a small set of inputs while still containing edge cases that need to be deliberately tested.

Instruction Set Architecture

The ALU was designed around our class-defined ISA, which used 16-bit instructions and supported operations including ADD, ADDI, SUB, LB, SB, BZ, and SLT.

The processor architecture included sixteen 8-bit registers, a 12-bit program counter, instruction memory, data memory, and a pixel-based output system. The ALU therefore had to fit into a larger datapath rather than functioning as a standalone circuit.

What I Learned

This project gave me practical experience translating computer architecture concepts into actual digital logic. More importantly, it taught me to think about hardware design as an iterative process: build a working model, test it, identify weaknesses, and improve the design.

It also gave me a better understanding of what happens beneath the software layer. Working with registers, arithmetic logic, instruction encoding, and datapaths helped connect the concepts I was learning in class to a functioning processor component.

Team Software Development Project

Yoink

Yoink is a web application designed to help students share leftover school supplies with other students instead of throwing them away. I worked on Yoink as part of a four-person development team, with my primary responsibilities focused on database design, user profiles, and user blocking.

Database Design

I took primary responsibility for designing the database schema and determining what information we needed to store and how that information should be structured. Yohance also helped with the database configuration while I focused mainly on the schema and data model.

The initial item structure included the item's name, status, image URL, location, description, and creation timestamp. I also implemented the initial database operations for creating and retrieving items.

User Profiles & Blocking

I built the user profile functionality that allowed users to view other users' profiles. I then developed the user blocking and unblocking functionality.

This required modifying the database, Flask routes, and frontend templates so that users could block others and have their posts removed from their item listings. I also added logic to account for users who had blocked the current user.

Redesigning the Blocking System

My first approach to implementing blocking was to store a list of blocked user IDs with each user. As I worked through the feature, I realized this was not the best way to structure the data.

I changed the database design and continued developing the feature using a better structure. This eventually allowed the application to support both blocking and unblocking while properly filtering posts based on user relationships.

Team Engineering

Yohance also made an important architectural improvement by introducing Flask Blueprints. This allowed us to separate our authentication, user, and item routes into different modules instead of keeping everything in one large application file.

I appreciated this change because it gave the project a much cleaner structure and made the codebase easier to navigate and maintain as we continued adding features.

What I Learned

Understanding how information flows through an application is just as important as getting an individual feature to work.

Yoink helped me understand how the database, backend routes, and frontend work together. I had to think about what data needed to be stored, how that data should be structured, and how changes in the database affected what users saw on the website.

I also learned that the first solution is not always the best solution. Redesigning the blocking system gave me practical experience evaluating a database design and improving it as the requirements became clearer.

Hardware Troubleshooting Project

Laptop Display Diagnosis & Repair

I worked on repairing a laptop with a faulty display. The repair required diagnosing the original problem, checking the device for possible water damage, finding a compatible replacement screen, and ultimately replacing a damaged display cable to return the laptop to working condition.

Diagnosing the Problem

The first step was determining whether the laptop had suffered water damage. After inspecting the device, I found no evidence of water damage, which allowed me to focus on the display hardware itself.

I then looked through a group of laptops that were scheduled to be disposed of and identified a screen that was compatible with the laptop I was repairing. I removed the compatible display and installed it on the laptop.

An Unexpected Failure

After installing the replacement screen, I wanted to verify that the original display was actually the source of the problem. During that testing process, the display cable began to burn. I immediately disconnected the system to prevent further damage.

At that point, the repair had become more complicated. The display cable was now damaged and needed to be replaced before the laptop could be returned to the employee.

Completing the Repair

I located a replacement display cable, installed it, and reconnected the compatible screen. After reassembling the laptop, I tested the display and confirmed that it was working properly. The laptop was successfully returned to the employee.

What I Learned

Sometimes the most important part of troubleshooting is knowing when you already have enough information.

This repair taught me an important lesson about troubleshooting: don't keep trying to "fix" a component that you have already determined is faulty without considering the risks of additional testing.

In this case, I could have left the original display disconnected after determining that it was not working. By attempting to test it again, I created an additional hardware problem that required replacing the display cable. Although I was able to recover from the failure and complete the repair, the experience changed how I approach hardware troubleshooting.

The experience reinforced the importance of controlled testing, understanding the potential consequences of each troubleshooting step, and knowing when stopping is the better technical decision.
